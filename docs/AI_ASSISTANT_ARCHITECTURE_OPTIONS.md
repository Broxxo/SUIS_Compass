# 嵌于应用内的全局 AI 助手：架构选项

## 目标愿景

- **一个智能体，高于应用层**：AI 助手是「始终在场」的智能体，而不是某个功能里的附属品。
- **主入口 + 处处可调**：既可以从主界面（SUIS COMPASS hub）的 AI 入口单独使用，也可以在任何子功能（课程河流、学生画像、课堂助手等）中调用。
- **上下文感知**：无论从哪里打开，助手都能获得「此时此刻」的上下文（当前在哪个应用、在看什么、在做什么），并据此给出帮助与建议。

---

## 参考：其他产品怎么做

| 产品 | 入口与形态 | 上下文如何注入 |
|------|------------|----------------|
| **Cursor** | 侧边栏聊天面板，快捷键唤起；同一面板在所有编辑场景可用 | 当前文件、选中内容、代码库索引自动注入 |
| **Notion AI** | 选中文字后菜单 / 斜杠命令；弹层或内联 | 当前页面、块内容、可选数据库 |
| **Microsoft Copilot (M365)** | 应用内固定图标，打开侧边栏或底部面板；Word/Outlook/Teams 同一套 | 当前文档、邮件、会议等随应用变化 |
| **Linear** | 侧边栏或全局 AI 入口；同一聊天界面 | 当前 issue、项目、迭代等 |
| **Intercom / 客服类** | 右下角固定小图标，全站一致；打开即聊天 | 当前页面 URL、用户信息、产品模块 |
| **Arc 浏览器 / Sidekick** | 侧边栏常驻，或快捷键 | 当前标签页、浏览上下文 |

**共性**：

1. **单一入口、单一聊天体**：不按功能拆成多个「小 AI」，而是一个助手多处可开。
2. **上下文由「当前场景」注入**：谁打开、在哪个页面、当前选中的实体（课程、学期、学生等）决定传给 AI 的 context。
3. **UI 形态**：多为**侧边栏**或**从侧边/底部滑出的面板**，少用悬浮球，避免遮挡且易扩展。

---

## 可选方案（按推荐度排序）

### 方案 A：顶栏全局入口 + 侧滑面板（推荐）

**做法**：

- 在 **AppTopBar** 的右侧（或固定位置）增加一个 **「AI」图标/按钮**，与语言、设置等并列；在主界面（CompassHub）和所有子应用（课程河流、学生画像、课堂助手）的顶栏都保留这一项。
- 点击后打开 **同一套 AI 聊天 UI**：从右侧滑出的面板（drawer）或居中大弹层；面板内仍是当前已实现的聊天 + 模型选择 + 快捷提问等。
- **上下文注入**：由「当前路由/视图」决定。例如：
  - 当前是 `CompassHub` → context = `{ screen: 'hub' }`，可选附带「最近打开的课程」等。
  - 当前是 Curriculum Roadmap 视图 → context = `{ screen: 'curriculum-roadmap', viewMode, courses, focusSemester, ... }`（即现有 gatherContext 的输入）。
  - 未来 `StudentPortrait` → context = `{ screen: 'student-portrait', currentStudent?, ... }`。
- 聊天历史可以**按场景分桶**（如 hub / curriculum-roadmap / student-portrait 各一份），也可以**全局一份**并在 system 里注明「当前所在场景」；后者实现更简单，且符合「一个智能体」的直觉。

**优点**：不遮挡内容、入口统一、易扩展；与 Cursor / M365 Copilot 的用法接近。  
**缺点**：需要把 AI 从「仅挂载在 Curriculum Roadmap 组件」改为「挂载在 App 层」，并由 App 或 Context 提供 context。

**移动端考量：入口放上方还是下方？**

- 导航栏在上方时，手机屏上**顶部区域拇指不易触达**，尤其大屏机单手操作时，把 AI 入口也放在顶栏确实会偏不方便。
- **底部更符合手机习惯**：多数移动端会把高频操作放在底部（如 iOS Tab Bar、Android 底部导航），客服/聊天类产品也常用右下角悬浮或底部固定入口，拇指更好够到。
- **建议：响应式放置**——同一套「顶栏入口 + 侧滑面板」逻辑不变，只让**触发按钮的位置**随视口变化：
  - **桌面 / 平板（如 ≥768px）**：AI 入口在 AppTopBar 右侧，与现在方案 A 一致。
  - **手机（如 &lt;768px）**：AI 入口放在**底部**，例如：
    - 固定底栏上单独一个「AI」图标（与「首页」等并列），或
    - 右下角小悬浮钮（FAB），不占顶栏空间。
- 点击后打开的仍是**同一个侧滑/弹层面板**，逻辑与数据完全一致，仅「打开按钮」在小屏时从顶部移到底部，兼顾桌面整洁与手机可操作性。

---

### 方案 B：可折叠侧边栏（常驻槽位）

**做法**：

- 在整体布局上增加一个 **右侧（或左侧）侧边栏槽位**，默认可折叠为一条窄边（只露图标）；展开后即 AI 聊天面板。
- 主界面与所有子应用**共用这一块区域**：切换课程河流 / 学生画像时，侧边栏不消失，只更新注入的 context。
- 上下文逻辑同方案 A：由当前 screen + 该 screen 提供的 payload 组成。

**优点**：助手「常驻」感最强，适合希望长时间开着聊天、边看内容边问的场景。  
**缺点**：占用横向空间，小屏需要做成 overlay 或全屏抽屉；布局改动较大。

---

### 方案 C：保留悬浮入口，但统一为「全局组件」

**做法**：

- 保留右下角悬浮按钮（可改为更小的 pill 或图标），但 **AI 聊天组件从 Curriculum Roadmap 里抽离**，提升到 App 层（与路由同级）挂载。
- 在 CompassHub、Curriculum Roadmap、未来的学生画像/课堂助手里，**都不再各自挂载 AIChatAssistant**，而是由 App 只挂载一次；当前 screen 通过 **Context（如 `AIContext`）** 提供 `contextPayload`（viewMode、courses、focusSemester 等）。
- 悬浮钮可在主界面隐藏、只在子应用显示；或全局显示，取决于产品偏好。

**优点**：对现有「悬浮球 + 弹层」改动最小，只是把组件提升并接上全局 context。  
**缺点**：悬浮仍可能遮挡内容，且入口在子应用里才出现时，主界面「单独使用 AI」需要另做入口（例如主界面也放一个 AI 按钮）。

---

### 方案 D：命令面板（Cmd+K）+ AI 为其中一项

**做法**：

- 做全局 **命令面板**（如 Cmd+K / Ctrl+K）：可搜索功能、跳转、执行操作。
- 其中一项为「打开 AI 助手」；触发后打开与方案 A 相同的滑出面板或弹层，并注入当前 screen 的 context。

**优点**：不占固定 UI，适合习惯快捷键的用户。  
**缺点**：发现性差，不常用的用户可能不知道有 AI；更适合作为**补充入口**，与方案 A 的顶栏按钮并存。

---

## 建议实施顺序

1. **先做多语言**（已完成）：AI 助手界面中英双语，方便中外教师。
2. **定入口形态**：采用 **方案 A（顶栏入口 + 侧滑面板）**；**移动端**小屏时 AI 入口放在底部（底栏或右下 FAB），大屏保持顶栏，响应式实现。
3. **抽象「上下文供给」**：定义 `AIContextPayload` 类型（如 `{ screen: string; ... }`），由各子应用在渲染时向 Context 写入当前 payload；AI 聊天组件只消费该 Context，不再从 props 拿 courses/focusSemester。
4. **主界面也可用 AI**：在 CompassHub 顶栏加入同一 AI 入口，注入 `screen: 'hub'`，必要时可附带「最近访问」等轻量信息。
5. **可选**：命令面板（方案 D）作为补充入口；或后续再考虑方案 B 的常驻侧边栏。

---

## 小结

- **多语言**：已按中英文双语落地 AI 助手界面。
- **架构方向**：采用 **顶栏全局入口 + 侧滑面板**（方案 A）；**移动端**小屏时 AI 入口改到底部（底栏或右下 FAB），兼顾手机拇指可及性。AI 组件提升到 App 层，由各子应用通过 Context 提供「当前场景」；这样既满足「嵌于应用、高于应用层」的展望，又避免悬浮球遮挡、且便于在任意功能中复用同一套助手与上下文逻辑。
